## 3. Подтверждённый блокер 1B-LEAVE-RESUME

**Старый незавершённый выход уничтожает список сообщений после того, как новый переход в тот же разговор уже вернул true.**

Исполнялась цепочка действующих функций из проверенного кандидата:

`chatBack.onclick → controller.navigate(home) → leaveConversationView → PablicusChat.leave (ожидание flush)`

Пока flush старого выхода не завершён:

`showConversationView → controller.navigate(conversation,c1) → handler conversation → mountConversationView`

После успешного нового перехода завершается старый flush. Настоящий метод `PablicusChat.leave` вызывает `list.destroy()` и устанавливает `list=null`. Проверка `isCurrent()` в leaveConversationView стоит после await, то есть после разрушения ресурса.

### Контрольные прогоны

| Сценарий | Результат | Наблюдение |
|---|---|---|
| Отказ от выхода | PASS | Полотно и список остаются; уничтожений 0; подтверждение 1. |
| Обычный завершённый выход без возврата | PASS | Маршрут home, current=null; список уничтожен один раз. |
| Подтверждённый выход → возврат до завершения flush | FAIL в 5 из 5 повторов | Новый переход вернул true, маршрут conversation/c1 и current=c1; затем list=null, destroy=1, open=0. |

В этих семи финальных прогонах не было ERROR или TIMEOUT. Фактические результаты сохранены в `1B_R2_RUNTIME_RESULTS.json`; компактная классификация — `1B_R2_RESULTS.json`.

### Корневая причина и почему это остаётся 1B

Ожидание выхода выполняется внутри обработчика перехода, но новое открытие того же conversationId считает старый разговор уже готовым. Незавершённое освобождение ресурса не согласовано с жизненным циклом нового перехода. Проверка после внешней асинхронной операции не отменяет уже выполненный ею эффект.

Это нарушение проверяемого контракта переходов и реальных callers, изменённых в данном 1B, а не предложение начать всю интеграционную программу 1C. Для воспроизведения не потребовались реальные аккаунты, IndexedDB или сервер. Нельзя переносить этот конкретный дефект в 1C для формальной приёмки 1B.

Существующая тестовая подмена `PablicusChat.leave` только увеличивает счётчик. Она не моделирует фактический destroy после await, поэтому 25 PASS не различают данный дефект. Это объясняет пропуск тестом; мотивы или намерения Исполнителя не устанавливаются.

**Установлено уничтожение ресурса списка сообщений. Потеря сохранённых сообщений, черновиков или байтов вложений этой пробой не измерялась и не заявляется.**

## 4. Воспроизводимость и происхождение

`review_real_leave.cjs` использует проверенную fixture Исполнителя только как механизм извлечения точных функций и подмены внешних границ. Сам сценарий состязания, положительные контроли и проверка реального leave добавлены независимо. Это не заявление о независимом переписывании всей тестовой обвязки.

Настоящий метод leave получен из `pablicus/chat.js:520` на TESTED_SHA, Git blob `4ff59d33af9fd587035d80e7134c225c5c00ffb2`; точная строка сохранена в `chat-leave.source.txt`. SHA-256 строки: `a02a6e1e7a08b6b7ceebc4226a627fb0a6383528e23457228cd6ea48e0d2d15e`.

Контроллер и app callers исполняются без изменения. Подменены DOM, SDK, flush и объект списка; последний позволяет наблюдать настоящий вызов destroy. Путь создания нового списка также учитывается, но в дефектном сценарии вообще не вызывается. Полный chat.js с реальным хранилищем не исполнялся.

Скрипт `review_r2_reproduce.py` проверяет точные Git blob SHA и ограничивает каждый процесс восемью секундами. Запуск на отдельном checkout TESTED_SHA или распакованном каталоге `1b/source` оригинального CI:

```sh
python docs/pablicus/reviews/2026-09-11/review_r2_reproduce.py \
  --source-root /path/to/tested-source \
  --output /path/to/review-r2-results.json
```

Скрипт намеренно привязан к a4e19bc и ожидаемо завершается кодом 1: два контрольных PASS, пять FAIL дефектного варианта. Для проверки исправленного кандидата Исполнитель должен добавить аналогичную регрессию в рабочий набор, а не объявлять ошибку проверки pinned SHA исправлением продукта. Систематический ERROR/TIMEOUT не считается воспроизведением.

## 5. Проверенные, но не блокирующие замечания

### Предел времени T06

Фраза «каждый сценарий 1B ограничен восемью секундами» не полностью точна: 1B-T06 выполняет пять последовательных node --check, каждый с отдельным пределом до 5 секунд; единого 8-секундного лимита всего T06 нет. Требование конечного выполнения обеспечено отдельными пределами. Достаточно точно описать это в обновлённом отчёте; отдельная перестройка runner ради данной формулировки не требуется.

### Уточнение ранней гипотезы о reject

В ходе проверки рассматривалась гипотеза: текущая ошибка mount может стать устаревшей во время await cleanup и попасть в новый экран. Первичный эксперимент содержал произвольно более строгое ожидание возврата false. Уточняющая инструментальная проба показала `screenAtDelivery=old`; новый экран после этого оставался действующим, необработанных отказов не было. Основания считать этот эксперимент доказанным дефектом не установлены. Он **не включён в блокеры и не требует изменения семантики текущего mount reject**. Сырые исследовательские результаты в пакете не равны приёмочным вердиктам.

## 6. Решение, границы и следующее действие

**Сохранить выполненное. Исправить один подтверждённый lifecycle-дефект 1B-LEAVE-RESUME, добавить регрессию через реальный leave, повторить набор и передать обновлённый кандидат.** Полный ограниченный промпт: `1B_COMPLETION_R2_PROMPT.txt`.

1B не принят; переход к 1C и последующим блокам не разрешён этим решением. 1A не повторяется; повреждённый патч не используется. Пятиблочный план не изменяется. Отсутствующий первоначальный промпт не реконструируется: действуют сохранённая коррекция и утверждённый план.

Технического препятствия доступу к необходимым доказательствам не было: GitHub-коннектор, скачивание CI и локальное исполнение работали. Данные других машин не проверялись. Причины возможных прежних сбоев локального Git Исполнителя приняты только как его документированное сообщение, не как новая ошибка этой проверки.

Main проверен отдельно. Отсутствие всех прошлых операций Исполнителя в Supabase не сертифицировано аудитом серверных журналов. Проверяющий runtime-код, main, production, Supabase и пользовательские данные не изменял. Разрешённая запись этой проверки — только документация и воспроизводимые доказательства в рабочей ветке; её коммит продвинет HEAD.
