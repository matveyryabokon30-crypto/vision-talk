# Пабликус: план развития действующего приложения

Пабликус создаётся как единая среда общения, работы с материалами, публикаций и выполнения задач людьми и ИИ. Основной путь продукта: **разговор → рабочий объект → действие → проверенный результат → повторно используемый сервис**. Чаты, Полотно, редактор, агенты и фабрика используют общие объекты, права и историю. Корневые разделы остаются **«Чаты / Дела / Вы»**.

Исходная точка на 13 сентября 2026 года — существующая веб-версия и приложение, установленное на телефоне владельца. Это план её последовательного развития. Утверждённый объём Plan 1.0 и дополнений 01/02/03 сохраняется. Публичная регистрация через ключ доступа уже работает; это не означает готовности всего первого полноценного релиза. Новый визуальный язык ещё требует предметной приёмки; прежние варианты «Орбита / Фолио / Реле» были отвергнуты.

Принятые инженерные результаты Block 1, 2A и ограниченной 2B сохраняют свои границы. ## 3. Продуктовые и дизайнерские ориентиры

**Контекстные действия и устойчивое рабочее пространство.** 72pt показывает, как вспомогательный выбор может раскрывать детали, сохраняя основной материал видимым. Codenotch даёт изучаемый открытый код геометрии края и привязанной карточки. Для Пабликуса рекомендуются один хозяин геометрии и один компонент выбора с различными представлениями. Нельзя строить отдельный несовместимый механизм для чата, Полотна и агента.[^1][^2]

**Материалы помогают различать управление и содержимое.** Apple описывает Liquid Glass как материал функционального слоя управления и навигации. Практический вывод для веб-версии: ограничивать прозрачные поверхности небольшими controls, сохранять непрозрачную читаемую основу содержимого, предусмотреть fallback. Перенос в CSS не воспроизводит автоматически системный материал SwiftUI. Красивый blur сам по себе не определяет продуктовый интерфейс.[^3]

**Агент становится участником работы с наблюдаемыми полномочиями.** Linear показывает делегирование агенту и доступ в рамках рабочих команд. Notion описывает управляемые источники, инструкции, запуски и историю собственного агента. Для Пабликуса отсюда следует отдельная сущность AgentRun: инициатор, исполнитель, разрешённый контекст, действия, расход, статус и проверенный результат. Человек должен понимать, что выполняется и как остановить работу.[^4][^5]

**Объект имеет несколько представлений.** BlockSuite сочетает документное и свободное представление поверх общих данных; Yjs предоставляет механизмы совместного состояния. Это подтверждает пригодность подхода «один объект — чат, редактор и Полотно». Внедрение совместного редактирования требует отдельной модели прав, долговечности и конфликтов; CRDT не решает эти задачи самостоятельно.[^6][^7]

**Возможности подключаются через ограниченный контракт.** MCP Apps описывает изолированный интерфейс, ресурсы и обмен сообщениями. Это применимо как ориентир для встроенных сервисов. Открытое выполнение произвольного кода с доступом к пользовательской сессии не является необходимым условием богатого интерфейса.[^8]

Это анализ выбранных первичных источников, а не статистический рейтинг всего рынка. Уровень Пабликуса определяется согласованностью поведения, реальными результатами и качеством на устройстве, а не числом визуальных эффектов.

## 4. Figma как конструктор собственной системы

Через подключённый Figma подтверждены Simple Design System, Material 3 Design Kit и Apple UI Kits, включая iOS/iPadOS 26 и 27. В SDS найдены Card, Form Log In, Form Register, Tabs и Search. Поиск выполнен в исследовательском файле `https://www.figma.com/design/ppVDFrQo8drbWCyxWtOHj1`; это контекст исследования, не утверждённый макет приложения.

Официальный SDS объединяет Figma-компоненты, токены, стили и примеры Code Connect с React-кодом. Репозиторий распространяется под MIT и помечен alpha. Его наиболее полезная часть для Пабликуса — воспроизводимая связь компонента с кодом и преобразование токенов в CSS. Это отдельная найденная библиотека: нельзя утверждать, что именно её использует автор uiux.build.[^9]

Последовательность работы: функциональный сценарий → экземпляры общих компонентов → варианты normal/focus/loading/error/disabled/empty → проверка на длинном русском тексте → связь со своим web-компонентом → выпуск в существующую PWA. Figma variables отражают семантические значения, например фон, текст, граница и акцент, а не случайные числа отдельных экранов. Компонентные варианты описывают состояния и назначение.[^10]

Готовая форма в Figma не реализует авторизацию. В сохранённом примере SDS обработчик `onSubmit` пуст. React-компоненты также не являются готовым подключением к текущей статической JS-архитектуре. Следует переносить подтверждённые решения через существующие `design-tokens.css`, `component-registry.js`, `controls.css` и AppShell. Полная миграция приложения на React ради UI-кита не обоснована.

Наборы Apple используются для изучения платформенного поведения с учётом их собственных условий. Собственные иконки, графика и типографический характер Пабликуса сохраняют приоритет Amendment 03. Покупка набора или постоянная платная визуальная зависимость этим планом не утверждается.

## 7. Что взять из OpenAI Academy

Builder Bootcamp охватывает Agents, Codex, Evals, RAG и production. Изучены программа и доступные текстовые материалы, а также описание сессии Agents; просмотр всех видеолекций не заявляется. Августовская программа API Builder Bootcamp добавляет последовательность API Foundations → Agents → Realtime → RAG → Production; занятие Production 16 сентября на дату этого плана ещё впереди.[^16][^17][^18]

Для разработки Пабликуса обучение превращается в конкретные результаты. API Foundations — один серверный запрос с лимитом и корректной обработкой ошибки. Agents — одно разрешённое действие над объектом с наблюдаемым результатом. RAG — поиск только по доступным материалам и цитата на конкретный источник. Realtime — отдельный проверяемый голосовой сценарий, когда основной текстовый путь работает. Production — стоимость, очередь, остановка, восстановление и диагностика.

Актуальные SDK-документы определяют технический контракт отдельно от учебной программы. На странице evaluation best practices есть уведомление о переводе Evals platform в read-only 31 октября 2026 и завершении работы 30 ноября. Поэтому предлагается хранить наборы примеров, ожидаемые результаты и исполняемый оценочный сценарий в своём Git, а внешнюю платформу выбирать после проверки её актуального статуса. Учебные ссылки на Evals нельзя без проверки сделать долгосрочной зависимостью.[^19][^20]

## 8. Общая архитектура ИИ

Три пользовательских режима работают на одной серверной основе: свободный AI CHAT; AI IN CONTEXT в конкретном разговоре или объекте; AI INLINE над выбранным текстом, вложением или вводом. Различаются допустимый контекст и способ открытия. Карточки из видео uiux.build подходят как ясные входы в эти действия, но фактическое исполнение принадлежит серверу.

Браузер передаёт идентификаторы разрешённых объектов, текст запроса и выбранное действие. Сервер проверяет сессию, членство и текущие разрешения, создаёт AgentRun, собирает минимальный контекст и вызывает модель/инструменты. Секреты провайдеров остаются на сервере. Вывод модели валидируется до сохранения и исполнения: модель предлагает действие, а адаптер проверяет его контракт и полномочия.

Минимальный AgentRun содержит `id`, `initiator_id`, `workspace_id`, `parent_run_id`, ссылки на входные объекты и их версии, allowed tools, бюджет, статус, события, результат и причину остановки. Состояния: queued, running, waiting_confirmation, completed, failed, cancelled. Result — отдельный долговечный объект с происхождением и связью с запуском. Модельный ответ «готово» не переводит задачу в completed без подтверждения нужной операции.

Для первого шага достаточно одного оркестратора и специализированных инструментов. Делегирование добавляется там, где меняется компетенция или бюджет: помощник → видеозадача; помощник → фабрика. У каждого дочернего запуска собственные права, предел шагов, timeout и результат. SDK упрощает цикл, но не заменяет серверные права, транзакции и продуктовые критерии.[^19]

## 9. Материалы, память, поиск и качество

Материалы: текст, PDF, DOCX и изображения. При загрузке проверяются размер, MIME, тип обработки, право доступа; оригинал сохраняется отдельно от извлечённого текста. Фоновая задача сообщает queued/processing/ready/failed. Для PDF сохраняются страницы, для текста — диапазоны, для изображений — ссылка на оригинал. Ответ с источником должен открывать тот материал, который действительно использовался.

RAG индексирует только квалифицированные материалы. Проверка прав выполняется и при поиске, и перед выдачей результата; фильтрация видимости лишь после передачи текста модели недостаточна. Удаление материала удаляет или инвалидирует производные индексы. При недостатке источников помощник сообщает об этом, а не дополняет пробел вымышленной цитатой.

Память пользователя отдельна от истории диалога. Пользователь видит сохранённые сведения, может исправлять, удалять и отключать их. Содержимое сторонних файлов, сайтов и ответов инструментов считается данными; инструкции внутри них не получают полномочий управлять приложением. Веб-поиск выдаёт проверяемые источники с временем обращения, а не изображает поиск без сетевого запроса.

Набор оценки хранится рядом с кодом: хорошие ответы, ожидаемые действия, недостаточный контекст, чужой объект, отозванный доступ, prompt injection, ошибка провайдера, отмена и повтор. Оцениваются доля задач с подтверждённым результатом, ошибки действий, достоверность ссылок, задержка и стоимость успешной задачи. Конкретные пороги закрепляются для сценария до реализации; усреднённый «AI работает» не является критерием.[^20]

## 10. Существующий открытый вход: подтверждённая основа

Публичная регистрация через ключ доступа уже реализована: `public-passkey.js`, `passkey-start.html/js`, custom OAuth provider `pablicus-passkey` и серверная Edge Function. Владелец подтвердил существующий вход через ключ и Face ID на телефоне. Повторное создание этой системы не является новой задачей развития.

Дополнительно выполнена реальная регистрация нового тестового пользователя в Chrome 153.0.8010.36 на публичном домене. Options/verify ответили 200; callback вернул в приложение; получена сессия; открылись «Чаты / Дела / Вы». Сервер подтвердил `is_approved=true`, одну identity и один связанный subject. Ручное одобрение аккаунта не потребовалось. Ключ был создан виртуальным WebAuthn authenticator: это проверка публичного серверного пути, а не самостоятельный физический тест Face ID. Приватный тестовый ключ сохранён локально и не включён в Git.

Самый быстрый путь к доступности приложения — использовать этот действующий вход и продолжать обновление существующей веб-версии. Названия кнопок, выбор режимов и дополнительные способы входа могут оцениваться в общем дизайне, если наблюдение за пользователями выявит препятствие. Они не должны превращаться в повторную реализацию уже работающей авторизации.

Дополнительный email-OTP возможен позднее как отдельный способ доступа после настройки production SMTP и подтверждения владения адресом. Стандартная почта Supabase имеет ограничения и не предназначена для массовой production-регистрации; OAuth-провайдеры также требуют собственной настройки. Эти возможности не являются условием использования уже работающего ключа доступа и не заявляются готовыми.[^21][^22]

Текущий `publicSignupReady=false` относится к почтовому пути и не означает закрытую регистрацию вообще. Обычные профили и trusted passkey activation имеют разные правила; массовое одобрение профилей не требуется. Публичное `mailer_autoconfirm=true` не доказывает владение email. Серверная активация существующего passkey связывает подтверждённый subject только с соответствующим новым профилем.

Доказательства и ограничения сохранены в AUTH_PUBLIC_ENTRY_R1.md и AUTH_EXISTING_SIGNUP_VERIFICATION.json. Повторный вход между устройствами и полная проверка всех правил доступа этим новым тестом не объявляются выполненными. Новых runtime-изменений Auth для подтверждения существующей функции не внесено.

## 11. Поэтапный выпуск в существующую веб-версию

Пять инженерных блоков сохраняются. Работающий публичный вход принят как существующая основа, а не шестой архитектурный блок и не новая задача реализации. Ни один этап не означает массовую одновременную замену приложения. Каждый ряд ниже разбивается на отдельные пользовательские результаты с собственным выполнением, проверкой и фиксацией.

| Этап | Результат в действующей веб-версии | Существующие точки интеграции | Условие завершения |
|---|---|---|---|
| Существующий вход | Регистрация нового пользователя подтверждена; Face ID подтверждён владельцем | public-passkey, passkey-start, сервер Auth | Сохранить работающее поведение при последующих изменениях |
| Block 2: восстановление | Возвращены подтверждённо потерянные функции; различимая версия | app-shell, shell.css, profile/search, sw.js | Воспроизведение → исправление → повтор, физический iPhone для соответствующих дефектов |
| Block 2: собственная система | Принятый общий control/поверхность на реальном сценарии | design-tokens, component-registry, controls, composer | Геометрия, состояния, длинный текст, доступность, сохранность рабочей области |
| Block 2: навигация и контекст | Spaces, Threads/Topics, общий поиск, Saved, identity и точки ИИ | controller, chat-list, tasks-home, people, composer | Разрешённый объект находится и открывается; чужой недоступен |
| Block 3 | Версионируемые сообщения и объекты, интерактивные действия | rich-message, rich-composer, chat-canvas, workspace-editor, transport-store | Один объект согласован в чате/Полотне/редакторе; старые сообщения читаются |
| Block 4 | Каналы/лента, роли, moderation, discovery и расписание | creation-flows, chat-library, public-bot-core, серверные политики/jobs | Два аккаунта видят разные права; публикация/отмена/жалоба дают подтверждённый результат |
| Block 5: помощник | Универсальный AI-чат и инструменты работы с материалами | существующая оболочка + сервер AgentRun/Result | История, источники, память, операции, бюджет, отмена, межустройственный возврат |
| Block 5: видео | Реальный редактируемый видеорезультат | media-viewer, объект проекта, квалифицированный Vision/worker | Исходник → операции → настоящий MP4 → правка → повторный результат |
| Block 5: фабрика | Работающий сервис из описания | bot-factory, bot-scenario-editor, service registry, изолированный runtime | Создан экземпляр, выполнен тестовый сценарий, результат и права проверены |
| Полный web-релиз | Все обязательные CATEGORY_A работают вместе | Те же опубликованные маршруты и общие данные | Сквозная приёмка, эксплуатационные ограничения и все доказательства |

Плановое время не подменяется обещанием «за один проход». Длительность следующей задачи оценивается после воспроизведения её исходного состояния и определения измеримого результата. Точные календарные сроки всего релиза без оценки существующих модулей, состояния SMTP и физической проверки были бы недостоверными.

## 12. Обязательный объём первого полноценного релиза

Следующая матрица удерживает полный утверждённый объём. Порядок реализации не исключает функции из обязательств; наличие пункта в плане не означает наличие работающего кода.

| Область | Обязательное содержание |
|---|---|
| Общение | Личные/групповые разговоры, вложения, согласованные черновики/outbox, каналы, лента и подписки |
| Контекст | Базовые Spaces/Communities, Threads/Topics, Global Search разрешённых сущностей, Saved/Personal Inbox, username/public identity без раскрытия телефона |
| Composer | Исправление, сокращение, расширение, перевод, тон, структура, преобразование в задачу/публикацию/действие агента |
| Interactive Messages | Buttons, choices, approvals, forms, task actions, agent actions, result actions |
| Rich Content | Text, headings, lists, tables, quote, code, media, file, form, task, agent result, service preview, carousel, safe embedded action |
| Рабочие объекты | Polls, Events, Checklists, Reminders, Lightweight Forms, Inline AI; устойчивые ID, версии, связи и восстановление |
| Роли | Owner, Admin, Moderator, Editor, Member, Guest, Agent; серверная проверка прав |
| Социальная эксплуатация | Report/block, moderation и аудит, базовое public discovery, scheduled messages/publications/reminders, recurring там, где применимо |
| Перевод и резюме | Различимы оригинал, перевод и AI-summary; доступны только разрешённые источники |
| Универсальный помощник | Свободный чат, история, поиск, переименование, экспорт, удаление, возврат между устройствами; текст/PDF/DOCX/изображения, управляемая память, реальный веб-поиск |
| Агентное выполнение | Три AI-режима; контролируемое делегирование; видимые инициатор, контекст, права, стоимость, статус и результат |
| Видео | Исходный материал, редактируемая модель операций, просмотр, реальный MP4 и правка по запросу; делегирование из универсального помощника |
| Фабрика | Описание → модули → ограничения → проверка → экземпляр сервиса; делегирование из помощника и реальная работа сервиса |
| «Возможности» | Базовый каталог; plugin/agent/bot/mini app/skill/integration/workflow как внутренние типы; UNVERIFIED / VERIFIED / PABLICUS_REVIEWED; видимые права |
| Встроенные сервисы | Ограниченный runtime, открытие из разговора/результата/профиля/канала/пространства, устойчивые deep links |

Модель связей остаётся `Message ↔ Thread ↔ Topic ↔ Work Object ↔ Agent Run ↔ Result`. Полотно — представление и место работы, не замена всем сущностям одним «сообщением». Опубликованный результат не должен раскрывать приватный объект через живую ссылку.

CATEGORY_B/C сохраняются в последующем развитии: звонки 1:1, групповые звонки/экран/комнаты/stage, развитые рекомендации, расширенный marketplace, QR-launch, бизнес-профили и передача человеку, монетизация после экономической квалификации. Commerce использует общие Merchant, Catalog, Product, Offer, Order, Booking, Checkout, Payment, Subscription, Fulfilment, Refund. Конкретный платёжный провайдер и автономные покупки этим планом не утверждаются.

## 13. Видео и фабрика: критерии реальной работы

Видео начинается с одного доказанного сквозного сценария. Пользователь добавляет материал, получает транскрипт/предложение операций, может изменить монтаж, запускает рендер и открывает файл с проверенными длительностью, кадрами и звуком. ИИ формирует ограниченный edit plan; движок исполняет детерминированные операции. Повторная генерация не уничтожает исходники и предыдущую версию. Выбор между браузерным рендером и worker принимается по реальному устройству, кодекам, памяти и очереди.

Фабрика сначала использует каталог проверенных модулей: форма, коллекция данных, список, правило, действие, уведомление, роль. Описание превращается в валидируемую спецификацию, затем в ServiceInstance с версией и тестовым сценарием. На выпуске проверяются создание записи, повторное открытие, права другого пользователя и ожидаемый результат. Текстовое ТЗ или красивый preview не называются созданным сервисом.

Длительные задачи исполняются вне короткого пользовательского запроса. Очередь, lease, idempotency, отмена, ограниченный retry и ссылка на результат позволяют вернуться к задаче после закрытия приложения. Пользователь видит понятное состояние, а технические идентификаторы остаются в диагностике.

## 14. Проверка, публикация и фиксация

Перед каждой задачей фиксируются исходный commit, пользовательский сценарий, границы изменения, критерий завершения и способ проверки. Выполняется одна задача; затем проверяются затронутый сценарий и действительно связанные регрессии. Для кода сохраняются совпадающие CODE_SHA и TESTED_SHA, результаты, ограничения и решение по следующему шагу. Документальная фиксация не присваивает инженерную или дизайнерскую приёмку.

Релиз должен иметь однозначный идентификатор и согласованный набор ресурсов. Изменение Service Worker проверяется через загрузку старой версии, появление новой, сохранение черновика, повторный запуск и возврат при ошибке. Проверка index.html по сети не подтверждает, что телефон использует тот же набор файлов. Отсутствие физического устройства обозначается отдельно от PASS браузерной эмуляции.

Для данных применяются совместимые миграции и проверка старых сообщений. Включение новой возможности проводится после её квалификации, а отказ отключает её без потери пользовательских объектов. Откат приложения не должен требовать удаления аккаунтов, истории или исходных файлов. При выпуске используются существующий домен и приложение; новая параллельная «демоверсия» не заменяет реальное внедрение.

## 15. Стоимость и эксплуатационные ограничения

Стоимость считается за успешно выполненную задачу: модель + вызовы инструментов + извлечение/индексация + рендер/worker + хранение/трафик + разрешённые повторы. До публичного включения ИИ задаются бюджет запуска, дневной лимит пользователя, предел длительности и аварийная остановка. Цены моделей и сервисов проверяются при выборе конкретного провайдера; этот документ не выдаёт неподтверждённые тарифы за бюджет.

Remotion имеет условия лицензирования, зависящие от использования и организации; tldraw также не является автоматически бесплатной production-основой.[^14][^15] Реестр зависимостей должен включать условия использования, обновление и заменимость. Ключи API принадлежат серверной конфигурации, не Figma, Git или браузерному bundle.

## 16. Ближайшие шаги

1. Зафиксировать карту существующих функций и конкретных пробелов на текущей опубликованной версии. Вход через ключ и Face ID уже существует; его повторное создание исключено из новых задач.
2. Закрыть подтверждённые регрессии Block 2 отдельными задачами. Связать идентификатор публикации и фактическую физическую проверку; сохранить аккаунты, историю и черновики.
3. Разработать один конкретный общий компонент на реальном сценарии Пабликуса с опорой на 72pt, собственную систему и найденные Figma/code-материалы. После предметной приёмки внедрить его в существующую веб-версию и проверить.
4. Последовательно довести общие рабочие объекты и социальные операции, сохраняя всю матрицу CATEGORY_A и фактически уже реализованные части.
5. На этой основе внедрить универсального ИИ-помощника, проверенный видеопроцесс и фабрику работающих сервисов. Каждый результат проходит цикл «задача → выполнение → проверка → фиксация».

Исследование, источники и полный план зафиксированы отдельно от реализации будущих функций. Новая регистрация на публичном сервере дополнительно подтверждена; установка и Face ID на телефоне подтверждены владельцем. Целевой дизайн и полный первый релиз ещё не приняты. Отсутствующие части прежнего чата, физическое состояние кэша телефона и проверки, которые не запускались, остаются явно обозначенными ограничениями.
