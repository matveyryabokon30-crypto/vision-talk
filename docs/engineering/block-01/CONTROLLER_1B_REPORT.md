## Что изменено по пяти пробелам

### 1. Реальный Auth, а не поиск строк

Тесты исполняют точные тела `onAuthStateChange`, `authenticate`, `clearSessionView` и продолжений восстановления из приложения. Внешние SDK-события и ответы профиля подменены на границе; проверяемые обработчики не переписаны внутри теста.

Событие SDK передаёт контроллеру свою идентичность напрямую, без дополнительного `getSession` внутри callback. Обновление токена и повтор события установленного пользователя не меняют поколения, не очищают экран и не загружают профиль повторно. Смена идентичности немедленно делает старое действие неактуальным. Поздний успешный/ошибочный ответ A не меняет пользователя, профиль и новый экран B.

Добавлены проверки ошибки/порядка получения сессии, восстановления с отложенным событием, ошибки восстановления с более новым входом и logout → повторный вход во время очистки. Явная идентичность аннулирует старые lookup-запросы; ошибка SDK не трактуется как logout. Повторная очистка ресурсов не выполняется. Изолированный неподтверждённый passkey-кандидат не становится текущим пользователем; подтверждённый путь сохранён. Серверный Auth и recovery-клиент не изменялись.

### 2. Отмена выхода с Полотна через настоящий caller

До исправления отдельно запущен реальный `conversationTab.onclick`: падающее утверждение `R4_REAL_CALLER_CANCEL` сохранено. Тот же финальный тест на WORK_START_HEAD повторно падает именно по этой причине, а не из-за среды.

Синхронный `beforeNavigate` выполняет `appNavigationAllowed` до публикации запроса, abort, cleanup и изменения маршрута. Публичные `showConversationView`, `showCanvasView`, `openConversation/goConversation`, обработчик «Назад» и программные переходы используют тот же контракт. Приватные рабочие функции вызываются уже после разрешения; повторного подтверждения нет.

При отказе в свежем CI: `confirm=1`, `hasUnsavedChanges=1`, `close=0`, `reset=0`, `abort=0`; маршрут, поколение, выбранная вкладка и dirty-состояние сохранены, активный ресурс Полотна остаётся. Дополнительно проверена отмена во время незавершённого `chatCanvas.open`: исходное открытие завершается успешно без отмены. Согласие даёт один prompt, чистое Полотно — ни одного. Переход Разговор → Полотно → Разговор сохраняет `conversationId=c1`, очищает посторонний `resourceId` и согласует screen/canvas.

### 3. Поздний reject старого действия

Исправная ранее реализация stale-rejection не переписывалась. Введён исполняемый сценарий: новый экран остаётся, oldActive=0, newActive=1, старая очистка=1, ложный успех=0, возврат старой операции=false, ошибка `late-old-rejection` зарегистрирована один раз, unhandled rejection отсутствует. Отдельно сохранены отказ текущего mount и ошибка cleanup.

### 4. Конечные ожидания и доказательство таймаута

Каждый сценарий 1B запускается в отдельной группе процессов с пределом 8 секунд. `node --check` ограничен 5 секундами на подпроцесс. JSON атомарно сохраняется до и после каждого теста; FAIL/ERROR/TIMEOUT/NOT_RUN не становятся PASS. При таймауте сохраняются имя, причина, лог, его SHA-256 и ненулевой результат, процессы останавливаются.

Контрольный `HARNESS_NEVER_FINISHES` намеренно создаёт незавершающиеся родительский и дочерний Node-процессы. В свежем CI: предел 0,5 с, фактически 0,5054 с; внутренний статус **TIMEOUT**, код процесса -15, код вложенного runner 1; оба PID уже не исполняются. PASS внешнего `1B-TIMEOUT-SELFTEST` означает правильную фиксацию отказа, не успех зависшего сценария.
