# Yandex UserInfo: кандидат серверного адаптера

Статус на 2026-09-08: исходный код и локальные тесты подготовлены. Функция **не развёрнута**; приложение Яндекс OAuth и провайдер Supabase **не зарегистрированы и не настроены** этим изменением. Реальный вход не проверен. Эти файлы нельзя публиковать как страницу GitHub Pages или подключать браузерным `<script>`.

Адаптер нужен для входа через существующий Яндекс ID без отдельного пароля Pablicus и без письма. Пользователь подтверждает вход на стороне Яндекса. Supabase обменивает OAuth-код, обращается к этому адаптеру с полученным токеном и сам создаёт сессию. Адаптер только проверяет токен через API Яндекса и переводит идентификатор в формат Supabase.

## Контракт

- Вход: `GET`, токен Яндекса в `Authorization: Bearer ...`.
- Единственный upstream: `GET https://login.yandex.ru/info?format=json`, заголовок `Authorization: OAuth ...`. Перенаправления запрещены.
- Обязательные проверки: ответ HTTP 200, корректный JSON, `client_id` строго равен `YANDEX_CLIENT_ID`, `id` — непустая строка допустимого размера. Числа не преобразуются в строки; субъект не выводится из почты, логина или имени.
- Успех: `{ "sub": "идентификатор-Яндекса", "name": "Имя, если есть" }`.
- Ответ никогда не содержит адрес почты, `email_verified`, токены, роли или исходный профиль. Имя — только отображаемый текст, не основание для доступа.
- Таймаут upstream — 5 секунд, максимальное тело ответа — 16 КиБ. Ошибки обобщены; код не журналирует заголовки, ответы или исключения. Все ответы имеют `Cache-Control: no-store`.

[Официальный контракт Яндекс UserInfo](https://yandex.ru/dev/id/doc/ru/user-information) описывает `client_id` и строковый `id` в JSON. Код намеренно отказывает при отсутствии этих полей. Если реальная конфигурация Яндекса их не вернёт, нужно выяснить причину, а не ослаблять проверку клиента.

## Что потребуется при реальном подключении

1. Зарегистрировать собственное веб-приложение **Pablicus** в [Яндекс OAuth](https://oauth.yandex.ru/client/new/id/). Достаточно права `login:info`; почта, телефон и доступ к почтовому ящику этому варианту не нужны.
2. Получить Callback URL из **Supabase → Authentication → Providers → New Provider** и внести его в Redirect URI приложения Яндекса. Не подменять его адресом самого Pablicus.
3. Развернуть оба файла `index.ts` и `handler.mjs` как одну серверную Edge Function `pablicus-yandex-userinfo` в существующем проекте `ctcoqgsztdtsazdiwcmd`. Публичный идентификатор приложения задать через `YANDEX_CLIENT_ID`. Client Secret хранить только в конфигурации OAuth-провайдера Supabase.
4. Для этой отдельной функции шлюз Supabase JWT должен иметь `verify_jwt=false`: входящий Bearer — OAuth-токен Яндекса, а не JWT сессии Supabase. Его обязательная проверка выполняется фиксированным API Яндекса внутри обработчика. Функция не использует `service_role`, не подписывает JWT и не имеет доступа к данным приложения. Не отключать проверку JWT для других функций.
5. Настроить `custom:yandex` по таблице в [OAUTH_PROVIDERS.md](../OAUTH_PROVIDERS.md), включая **`email_optional: true`**, и указать URL реально развёрнутой функции как UserInfo URL.
6. Выполнить проверенную серверную настройку создания/активации новых профилей, обработку OAuth-возврата в клиенте, затем настоящий вход и проверку изоляции чатов. Только после этого включать пункт Яндекса в опубликованном интерфейсе.

Необходимый адрес функции после развёртывания с указанным именем:

`https://ctcoqgsztdtsazdiwcmd.supabase.co/functions/v1/pablicus-yandex-userinfo`

Это **планируемый адрес**, его работоспособность не подтверждена.

## Почему email отсутствует

API Яндекса не предоставляет документированный `email_verified` в рассмотренном JSON-контракте. Поэтому адаптер не заявляет, что подтвердил владение адресом. Документированный режим Supabase `email_optional=true` позволяет использовать аутентифицированную пару **провайдер + субъект**, не передавая email вообще. Непустой неподтверждённый email снова включил бы процедуру подтверждения письмом.

Такой первый вход создаст отдельный аккаунт Яндекс ID. Он **не объединяется автоматически** с существующим аккаунтом Pablicus по совпадению имени или адреса. Сохранение старого аккаунта при добавлении Яндекса требует отдельного явного связывания в уже авторизованной сессии Pablicus.

## Активация профиля

Существующий триггер Pablicus не поддерживает нового OAuth-пользователя без email. Даже успешная выдача сессии Supabase сейчас не гарантирует доступ в мессенджер. Требуется отдельно проверенная серверная схема из [SERVER_SETUP.md](../SERVER_SETUP.md) с дополнением для OAuth:

- создать корректный уникальный username даже при пустом email;
- пометить только новый неподтверждённый профиль как ожидающий активации;
- после серверной вставки в `auth.identities` активировать такой профиль только для разрешённого точного провайдера `custom:yandex` и непустого `provider_id`;
- доверять серверной записи identity, не `raw_user_meta_data` и не входному параметру браузера;
- не менять старые заблокированные/неодобренные профили и не восстанавливать потреблённое ожидание активации;
- сохранить проверку членства в переписках, RLS, права на файлы и возможность блокировки.

В этой папке нет SQL, изменений базы или готовой миграции. Нельзя просто удалить клиентскую проверку `is_approved`.

## Проверка

```sh
node --test apps/pablicus/public-access/yandex-userinfo/handler.test.mjs
```

Девять локальных тестов используют только подставной `fetchImpl`: отправка токена на фиксированный endpoint, минимальный успешный ответ, отсутствие утечки email/токенов/ролей, отказ для чужого клиента и некорректного субъекта, неправильная авторизация/метод без upstream-запроса, ошибки, лимит размера и таймаут. Это не проверка настоящего Яндекс OAuth или развёрнутой Edge Function.

Для приёмки нужны реальный OAuth-вход, отказ при отмене согласия, повторный вход в тот же профиль, отсутствие письма, отсутствие неявной привязки к старому email-профилю, сохранение старых блокировок и раздельный доступ к перепискам/файлам с нескольких аккаунтов.
