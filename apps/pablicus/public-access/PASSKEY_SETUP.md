# Pablicus: ключ доступа и Face ID

Решение владельца от 8 сентября 2026: реализовать ключ доступа с подтверждением через Face ID. Для веб-версии это WebAuthn/passkey: биометрия обрабатывается устройством, сервер проверяет криптографическое подтверждение. Браузер может предложить также отпечаток, код устройства или совместимый менеджер ключей; приложение не обещает обязательный Face ID на любом устройстве.

## Что реализуется

- Кнопка «Создать ключ доступа» в профиле существующего пользователя.
- Кнопка «Войти с ключом доступа» на странице входа.
- Настоящие API Supabase Auth и браузерный WebAuthn; проверка пользователя и одобрения профиля до доступа к чатам.
- Отмена запроса, повторная попытка, отсутствие поддержки браузером, проверка смены аккаунта, список сохранённых ключей.
- Существующий пароль, восстановление и данные аккаунта сохраняются. SMS и QR в этот этап не входят.

SDK обновлён с 2.45.3 до официального 2.105.0 с проверяемой целостностью. Минимальная версия и экспериментальный статус API подтверждены [документацией Supabase](https://supabase.com/docs/guides/auth/passkeys). В `src/auth-config.js` готовность `passkeys.enabled` по умолчанию `false`; она не включает функцию на сервере. Наличие кода не означает рабочий Face ID на опубликованном сайте.

## Настройка существующего проекта

Открыть [Authentication → Passkeys](https://supabase.com/dashboard/project/ctcoqgsztdtsazdiwcmd/auth/passkeys) в проекте **Vision talk**.

| Поле | Значение для текущего опубликованного сайта |
|---|---|
| Enable Passkey authentication | Включить |
| Relying Party Display Name | `Pablicus` |
| Relying Party ID | `matveyryabokon30-crypto.github.io` |
| Relying Party Origins | `https://matveyryabokon30-crypto.github.io` |

RP ID и origin не содержат `/vision-talk/pablicus/`: браузер ограничивает ключ доменом, а не путём. При смене RP ID существующие ключи перестанут работать; переход на собственный домен требует отдельного плана. Нативная iOS-версия позднее потребует Associated Domains. Веб-ключи не требуют регистрации «Войти с Apple».

После сохранения настроек нужны проверка серверного ответа, включение публичного флага в сборке, публикация и испытание на настоящем устройстве: создать ключ в своём профиле, выйти, войти этим ключом в тот же аккаунт, проверить отмену и сохранение переписки. Виртуальный аутентификатор в CI не подтверждает работу физического Face ID или iCloud-синхронизации.

## Наблюдённый доступ и ограничения

На 8 сентября 2026 текущая SQL-сессия использует `supabase_read_only_user`, `transaction_read_only=on`, без CREATE public/UPDATE profiles. В auth присутствуют таблицы `webauthn_credentials` и `webauthn_challenges`; содержимое ключей не читалось. GET `/auth/v1/settings` доступен, но не сообщает готовность passkeys. Единственная проба POST `/auth/v1/passkeys/authentication/options` не завершилась: сетевое согласование было отменено до решения. Повтор через другой канал для обхода отмены не выполнялся.

Инструменты текущего подключения не предоставляют изменение конфигурации Auth. Не обходить это ролью, SECURITY DEFINER, доступом к чужим токенам или извлечением секретов. Вход владельца в кабинет на его iPhone не создаёт административную сессию в браузере помощника. Серверная активация и физический вход пока не подтверждены.

## Первое создание нового аккаунта

Штатный Supabase passkey API требует существующего подтверждённого неанонимного пользователя. У владельца такой аккаунт уже есть. Добавление ключа к нему не требует сброса пароля или изменения профиля.

Строгий новый сценарий «анкета → ключ → доступ без почтового или телефонного подтверждения и без пароля» не реализуется одним `signInAnonymously()` с последующим `registerPasskey()`: Supabase запрещает регистрацию ключей анонимным пользователям. Текущий модуль не создаёт вымышленные email, не включает глобальное автоподтверждение, не переименовывает неподтверждённый контакт в подтверждённый и не обходит этот серверный запрет. Для такого первого создания нужно отдельно спроектировать и развернуть поддерживаемую серверную авторизацию с сохранением членства и изоляции чатов. Предыдущий проект изменения публичной регистрации в `SERVER_SETUP.md` также ещё не применён.

## Восстановление

Ключ человек не придумывает и не запоминает. Его доступность на другом устройстве зависит от выбранного менеджера и синхронизации. Для имеющихся аккаунтов прежний пароль и восстановление сохраняются. QR-перенос, резервные коды и бесконтактное восстановление новым кодом не добавлены. Нельзя обещать восстановление, если пользователь потерял все ключи и все заранее настроенные способы подтверждения.
